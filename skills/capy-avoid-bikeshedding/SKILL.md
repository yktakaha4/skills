# 自転車置き場の議論を避ける

利用者が受け取る価値を変えない実装上の選択には、プロジェクトで予測可能な既定値を使う。好みの表明や独自規則の追加ではなく、既存の流れに沿った最小で理解しやすい実装へ収束させる。

ユーザーに選択または承認を求める場合は、環境が提供する構造化された選択・承認UIを使用する。適切なUIがない場合だけ、テキストで選択肢や回答方法を提示する。

## 対象と成果を確認する

1. 依頼された変更の目的、利用者から観測できる挙動、完了条件、互換性、性能、安全性、運用上の制約を確認する。
2. 現在の変更範囲と、議論または差分を生んでいる箇所を特定する。コードだけでなく、設計案、レビューコメント、テスト、文書、設定も確認する。
3. 外部から観測できるcontractを維持したまま整理するのか、挙動変更も依頼されているのかを区別する。整理を理由に依頼範囲を広げない。

## 自転車置き場の論点を分類する

次のような選択肢の違いが利用者、正確性、安全性、運用、互換性、意味のある保守コストへ影響しない場合は、議論すべきproduct decisionではなく規約へ収束させる実装詳細として扱う。

- formatterが決められる空白、改行、括弧、引用符、import順
- 意味が同等な識別子の表記や語順
- 小さな処理を関数へ抽出するか、その場に置くか
- 密接な処理を同一moduleに置くか、細かなfileへ分割するか
- 同程度に理解できる標準構文、collection操作、制御構造の選択
- 利用者に見えず、計測可能な差もない内部配置や記述順

次の事項は自転車置き場の議論として切り捨てない。

- 公開API、出力、アクセシビリティ、国際化、エラー表示など利用者が観測する挙動
- correctness、security、privacy、data integrity、resource消費、latency、reliability
- migration、rollback、互換性、障害対応、監視、testabilityへ実質的に影響する設計
- ownershipや依存方向を曖昧にし、将来の変更コストを明確に増やすmodule境界
- リポジトリの規則、言語仕様、framework contract、toolingの制約に反する選択

影響があるか不明な場合は、好みを議論する前に既存コード、計測、仕様、最小の検証から事実を確認する。

## 既定値を優先順位どおりに選ぶ

実装上の選択は、次の順序で決める。上位の根拠が十分なら下位の代替案を並べない。

1. 対象pathに適用される`AGENTS.md`、contribution guide、style guide、architecture decision、生成規則
2. formatter、linter、compiler、framework設定と、自動生成またはscaffoldされた正規の形
3. 同じ責務を持つ隣接コードと、リポジトリ全体で一貫している実装パターン
4. 使用中の言語、標準library、framework、ecosystemで広く採用される標準的な方法
5. 追加の抽象化、設定、依存関係を必要としない、最も単純で局所的な方法

古いコードが複数の流儀を含む場合は、単純な多数決をしない。対象に最も近く、現在も保守され、同じ責務とruntimeを持ち、現行toolingを通過する実装を優先する。deprecatedな例や移行途中のpatternを踏襲しない。

## 命名と実装粒度を揃える

- domainで既に使われている語彙を再利用し、同じ概念に新しい同義語を作らない。
- 名前は役割と観測可能な責務を表す長さにする。型や文脈から明白な情報を重ねず、独自の略語や比喩を導入しない。
- 一度しか使わない短い処理を、見た目を整える目的だけで関数にしない。一方、独立した規則、error handling、再利用、単体検証に意味がある処理は既存の粒度に合わせて分ける。
- fileやmoduleは、明確な責務、依存方向、公開境界がある場合に分ける。行数だけを理由に分割せず、無関係な責務を一つへ押し込めない。
- wrapper、helper、interface、factory、base classなどの抽象化は、現在ある複数の具体例またはproject規則が要求する場合に使う。将来必要になるかもしれないという理由だけで追加しない。
- コメントはコードから分からない制約や理由を説明する場合だけ残す。自明な処理、命名議論、試行錯誤の経緯を記録しない。

## 議論を生まない形へ修正する

1. 変更箇所を選択した既定値へ揃え、無関係な周辺コードの一括整形や命名変更を混ぜない。
2. 同じ目的の重複helper、薄いwrapper、不要な中間層、細かすぎるmodule、放棄された代替実装を、contractを保ったまま除く。
3. formatterやlinterが決定できる事項はtoolへ委ね、手作業の好みを新しい規則として文書化しない。
4. ecosystem標準を採用するためだけに、新しい依存関係、設定file、build stepを安易に追加しない。既存toolingで表現できない規則を追加する場合は、議論コストを上回る具体的利益が必要である。
5. レビューコメントや文書から、最終成果に不要な候補列挙、個人の好み、実装過程の弁明を取り除く。採用した形の根拠が必要なら、参照した既存規約または周辺実装を短く示す。

複数の案が同等なら、推奨候補をいくつも提示してユーザーへ選ばせず、優先順位に従って一つを採用する。既存の根拠がなくても、安全で可逆かつ局所的なら、ecosystem標準または最も単純な案で進める。

## 判断を求める境界

次の場合だけ、選択肢、利用者や運用への影響、推奨案を整理してユーザーへ判断を求める。

- 選択によって公開contract、挙動、performance、security、data、互換性、運用負担が実質的に変わる。
- project内の明示的な規則が矛盾し、どちらを正とするかで今後の変更範囲が大きく変わる。
- 標準的で単純な案では要件を満たせず、独自の抽象化や長期的な保守負担が必要になる。
- 広範なrename、module再編、公開済みinterface変更など、reviewやrollbackのコストが高い。

「どの名前が好みか」「何行で関数を分けるか」のように、規約と周辺実装から決められる質問をユーザーへ戻さない。好みしか根拠がない変更案は採用も提案もしない。

## 検証して報告する

1. 対象となるformatter、linter、型check、testを実行する。
2. 最終diffを確認し、利用者向けcontractが意図せず変わっていないこと、無関係なstyle差分が混ざっていないことを確認する。
3. 命名、関数粒度、module境界が、参照した規約または周辺実装と一貫しているか確認する。
4. 報告では、維持した外部挙動、揃えた既存pattern、実行した検証、残る実質的なtradeoffだけを示す。検討した同等な候補や主観的な好みを列挙しない。

規約が存在しないことを理由に新しいstyle guideを作らず、今回の変更に必要な最小の前例を残す。将来同じ選択が繰り返し問題になる証拠が得られた場合だけ、別の明示的な依頼としてtoolingや規約化を提案する。
