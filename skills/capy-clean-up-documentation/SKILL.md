# 記述を実装に合わせて整理する

読者が現在のsystemを正しく利用、変更、運用するために必要な情報だけを残す。記述量ではなく、正確性、必要性、発見しやすさを改善する。

ユーザーに選択または承認を求める場合は、環境が提供する構造化された選択・承認UIを使用する。適切なUIがない場合だけ、テキストで選択肢や回答方法を提示する。

## 対象と根拠を確認する

1. 対象pathに適用される`AGENTS.md`、contribution guide、文書規則、生成規則を確認する。
2. 依頼範囲と、想定読者が文書から達成すべき作業を特定する。無関係な文書の一括整理へ範囲を広げない。
3. README、ガイド、設計文書、API説明、例、コメント、docstring、設定内の説明を検索し、対応する実装、設定、テスト、schema、CLIの出力など実行可能な根拠へ対応付ける。
4. 現在の挙動、外部へ約束したcontract、意図や理由、過去の記録を区別する。実装から確認できない記述を推測で補わない。

容易に実行できる場合は、コマンド、例、既定値、error message、生成手順を実際に検証する。テストだけを仕様の証明とはみなさず、公開interfaceと利用者が観測する挙動も確認する。

## 記述を分類する

各記述を次のいずれかに分類してから編集する。

- **残す**: 公開contract、前提条件、非自明な制約、安全上の注意、設計理由、運用手順、失敗時の対処など、実装を読むだけでは適切に判断できない情報
- **短くする**: 正しいが重複している説明、要点より長い背景、同じ意味の言い換え、過剰な見出しや例
- **削除する**: 名前や型から明白な内容、コードを逐語的に説明するコメント、放棄された案、試行錯誤の弁明、実体のない将来構想、別の正本を不完全に複製した内容
- **修正する**: 現在の実装、設定、公開contractと一致しない値、手順、名称、例、link、責務の説明
- **補う**: 読者が正しく利用、変更、運用するために不可欠で、確認可能な根拠があるのに欠けている情報
- **保全する**: ADR、作業ログ、変更履歴、release note、migration記録、incident記録など、特定時点の判断や事実を保存する文書

短いことだけを理由に有用な説明を消さず、長いことだけを理由に分割しない。コメントは処理内容ではなく、コードから分からない理由、制約、危険、外部仕様との関係を説明する場合に残す。

## 現在の文書を整理する

1. 同じ情報に正本を一つ定め、他の箇所は削除するか、必要なら正本への短い参照に置き換える。
2. 実装を逐語的に説明する段落やコメントを削除する。読者が実装を探すために必要な入口まで失わない。
3. 古い名称、既定値、コマンド、出力例、file構成、責務、対応状況を、確認した現在の事実へ修正する。
4. 必須の前提、公開contract、非自明な制約、security上の注意、検証方法が不足していれば、根拠を確認して最小限補う。
5. 読者が行動できない抽象的な主張、成果の自己評価、過剰な強調、生成AIらしい定型的な導入やまとめを削る。
6. 最終的な文書を最初から読み直し、削除によって参照、段落、手順、番号、例の前提が壊れていないことを確認する。

文書の整理を理由に実装の挙動を変更しない。記述の正しさを判断するためのread-onlyな調査と検証を先に行い、別の修正が必要なら分離して扱う。

## 過去の記録を保全する

ADRや作業ログなどは現在の説明書ではなく、当時の判断と経緯の記録として扱う。

- 現在の実装と異なるという理由だけで、過去形の記述、当時の選択肢、決定理由、日付、結果を書き換えない。
- 読みやすくするための要約、用語の現代化、現在の状態への置換を行わない。
- 明白な誤記を直す必要がある場合も、記録の意味や当時の主張を変えない。意味が変わる可能性があれば編集しない。
- 現在の状態を伝える必要がある場合は、既存の形式に従って`Superseded`などのstatus、後続ADRへのlink、または日付付きの追記を使う。過去の本文を現在形へ書き換えない。
- 履歴文書か現在の規範文書か判別できない場合は、file名だけで決めず、日付、status、配置、参照元、リポジトリ規則を調べる。それでも不明なら保全側に倒す。

## 規範文書と実装の乖離を扱う

ガイドライン、design document、仕様書など、将来の変更を拘束し得る規範文書が実装と乖離している場合は、どちらかを黙って正としない。まず、実装、テスト、公開contract、変更履歴、文書のstatusから、現在の挙動と文書の主張を具体的に示す。

次のような相互排他的な選択肢を、影響と推奨案を添えてユーザーへ提示する。

- 実装が意図した現在の挙動なら、規範文書を実装へ合わせて修正する。
- 文書が目標状態を表すが実装変更は今回の範囲外なら、乖離、影響、解消条件を明記し、追跡先へ結び付ける。
- 文書が正しいcontractで実装が欠陥なら、文書を維持し、実装修正を別の挙動変更として扱う。

根拠だけで一意に決まる誤記は局所的に修正してよい。選択によって公開contract、将来の実装方針、互換性、運用が変わる場合は、整理作業の一部として決めつけない。乖離を単に「既知」と書くだけで放置せず、対象、実際の挙動、影響、解消方針または追跡先を明確にする。

## 検証して報告する

1. 文書用のlinter、link check、example test、doctest、生成checkなど、対象に適用される検証を実行する。
2. 記載したコマンドや例を安全に実行できる範囲で再確認する。実行できないものは未検証と明記する。
3. 最終diffを読み、事実に根拠があること、必要なcontractや理由を失っていないこと、履歴記録を現在の説明へ改変していないことを確認する。
4. 報告では、削除または統合した記述、修正・補足した重要な事実、根拠と検証結果、保全した履歴文書、未解決の乖離だけを簡潔に示す。

削除した文章の一覧や編集過程を新しい文書として残さない。整理後の成果物そのものを、現在の正確な説明として完結させる。
