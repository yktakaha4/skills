# ホビープログラミングとして扱う

対象をホビープログラミングとして明示し、現在確認できる必要性に釣り合う最小の設計を選ぶ。仕事向けの運用を根拠なく持ち込まず、変更しやすく理解しやすい状態を保つ。

ユーザーに選択または承認を求める場合は、環境が提供する構造化された選択・承認UIを使用する。適切なUIがない場合だけ、テキストで選択肢や回答方法を提示する。

## 適用範囲を確定する

1. ユーザーがこのスキルを明示的に指定した場合だけ適用する。リポジトリの規模、個人名義、利用技術からホビープロジェクトだと推測しない。
2. 対象となるリポジトリ、機能、作業期間を確認する。この宣言を無関係な別プロジェクトへ引き継がない。
3. `capy-declare-professional-project`も同時に指定されている場合は方針を混ぜず、どちらを対象に適用するかユーザーへ確認する。
4. 既存のプロジェクト規則、現在の利用者、保存データ、公開範囲、外部連携、費用、安全上の制約を確認する。ホビーという宣言で、確認済みの制約を無効にしない。

## 現在の必要性から設計する

- 実際の利用者、入力、データ量、実行頻度、利用環境を基準にする。根拠のない将来の組織拡大、マルチテナント化、世界規模のトラフィックを前提にしない。
- 非機能要件は、現在の使い方に必要な応答時間、信頼性、費用、保守性だけを具体化する。測定も利用予定もない目標値を作らない。
- 標準library、既存の依存関係、単一の明確な処理経路、少ない設定を優先する。
- 現在一つしかない実装のために、plugin機構、汎用framework、抽象interface、分散構成、複雑なcacheやqueueを先回りして追加しない。
- 将来の可能性ではなく、現在繰り返されている変更や実測された問題がある場合だけ抽象化、分割、最適化を行う。

## 単純化する変更を選ぶ

1. 既存挙動と必要な成果を特定し、それを満たす最短の保守可能な変更を選ぶ。
2. 互換性layer、移行用の二重実装、未使用の拡張point、不要になった設定を維持するコストと、破壊的変更の影響を比較する。
3. 破壊的変更によって実装、データmodel、設定、利用手順を大幅に単純化でき、現在の利用者が移行可能なら候補にする。
4. 破壊的変更の対象、失われる互換性、データへの影響、再作成または移行手順、rollback可否を示す。データ削除、履歴書き換え、公開interface変更などは実行前にユーザーの承認を得る。
5. 旧方式を残す具体的な利用者や移行期間がなければ、恒久的なcompatibility codeを追加しない。必要な場合も終了条件を定める。

破壊的変更を目的にせず、単純化の利益が移行コストと事故リスクを明確に上回る場合だけ選ぶ。

## レビューと実装の基準を調整する

- 現在到達可能な不具合、データ損失、秘密情報の露出、実測された性能問題、理解しにくさを優先して扱う。
- 想定利用量では発生しないscale上の懸念や、具体的な要件のないenterprise向け機能を必須指摘にしない。
- 「将来必要になるかもしれない」だけの抽象化、設定、テスト、運用基盤を追加しない。
- 小さなプロジェクトでも、正確性、credential保護、入力検証、復元困難なデータのbackup、主要経路のテストは省略しない。
- 自動化の保守コストが手作業より高い場合は、再現可能な短い手順を選ぶ。頻度や失敗実績が増えたら自動化を再検討する。

## 検証して報告する

1. 現在の利用方法を代表するテストまたは手動手順で変更を確認する。
2. 破壊的変更を選んだ場合は、古い状態からの移行または再作成と、変更後の通常操作を確認する。
3. 報告では、ホビープロジェクトとして採用した規模と運用の前提、単純化した内容、維持した安全策、未検証の点を分けて示す。
4. 利用者、データ価値、公開範囲、負荷が前提を超えた場合に再検討すべき事項だけを残す。

ホビープログラミングを低品質の理由にせず、不要な複雑さを避けるための判断基準として使う。
