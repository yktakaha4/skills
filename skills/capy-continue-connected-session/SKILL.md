# 接続セッションを観測して作業を継続する

それまでの会話を目的と制約の根拠にし、接続中のターミナル、ブラウザ、実行中アプリを現在状態の一次情報として扱う。観測結果から期待される次の操作を特定し、依頼範囲内で安全に作業を進める。エラーがある場合はトラブルシュートを行うが、エラー診断だけを目的とするスキルではない。

ユーザーに選択または承認を求める場合は、環境が提供する構造化された選択・承認UIを使用する。適切なUIがない場合だけ、テキストで選択肢や回答方法を提示する。

## 会話から期待される作業を復元する

1. 直前の発話だけでなく、それまでの会話から目的、完了条件、明示された制約、すでに実施した操作、未完了の作業を整理する。
2. ユーザーが指す「これ」「続き」「今の画面」を、接続中のterminal、browser、process、repository、URL、taskと対応付ける。対象が複数ある場合は、時刻、command、port、branchなどで識別する。
3. 現在状態を観測すれば一意に決められる事項を、先にユーザーへ質問しない。会話上の目的から自然に導ける可逆で局所的な次の操作は、根拠を持って進める。
4. 会話から読み取れない目的、対象、または重大なtradeoffが残り、推測すると依頼範囲を外れる場合だけ確認する。
5. リポジトリ内で作業する場合は、編集前に`AGENTS.md`などの指示、Git状態、テスト手順を確認し、ユーザーの既存変更を保全する。

## 接続中の状態を直接観測する

### ターミナル

- 現在のprompt、直近の完全なcommand、exit code、標準出力と標準エラー、processが実行中か終了済みかを確認する。
- 出力の切れた末尾だけで判断せず、必要な範囲まで遡る。長時間処理は状態をpollし、同じcommandを重複実行しない。
- 入力待ち、承認待ち、pager、interactive promptを、停止や失敗と取り違えない。

### ブラウザと実行中アプリ

- 現在のURL、表示内容、dialog、error、loading状態、操作可能なelementを確認する。
- 必要に応じてdeveloper console、network request、server logを対応付ける。画面だけで完了を判定できない場合は、結果を示す別の観測点も確認する。
- ユーザーのsigned-in sessionを利用できる場合も、公開、送信、購入、削除、権限変更などの外部副作用は依頼と承認の範囲内に限定する。

### 機密情報

- token、cookie、password、authorization header、秘密鍵、個人情報、`.env`の値を表示、転載、保存、コミットしない。
- 必要なら値を伏せ、存在、形式、長さ、権限など秘密を露出しない属性だけを確認する。

確認済みの事実、そこから導いた推定、まだ確認していない仮定を区別する。接続状態と矛盾する古い会話情報は現在の観測で更新するが、目的や権限を勝手に拡張しない。

## 観測結果に応じて作業を進める

1. 実行中なら、完了、入力要求、失敗、またはユーザー判断が必要な状態まで適切に追跡する。
2. 正常に完了していれば、出力と成果物を確認し、会話上の次工程へ進む。結果確認だけを依頼されている場合は、不要な変更を加えない。
3. 入力や承認を待っていれば、内容と影響を確認し、安全かつ依頼範囲内なら応答する。特権、破壊的操作、課金、公開、秘密情報、productionなどに関わる場合はユーザー判断へ引き渡す。
4. 失敗していれば、観測、仮説、最小再現、安全性の分類、原因修正、同じ観測点での再確認を行う。典型的なエラー文字列だけで原因を確定しない。
5. safeなworkspace内の修正を依頼されている場合は、最小の変更を実装して検証する。ユーザーがread-only、診断のみ、またはコミット不要と指定していなければ、リポジトリ方針とbranchを確認したうえで今回の修正だけをコミットする。
6. 特権操作、復元困難な削除、履歴書き換え、productionや共有環境への変更、安全機構の無効化、長期的に不利なworkaroundは自動実行しない。影響、前提、限定した手順、rollbackを示してユーザー判断を求める。
7. 元の目的に対する完了条件を、terminal、browser、成果物、testなど適切な観測点で確認する。一度成功した、processを再起動した、error表示が消えたという事実だけで根本解決やタスク完了と報告しない。

## 接続先を参照できない場合

接続中のterminalやbrowserが存在するはずなのに参照できない場合、手元の会話や一般論だけから現在状態を推測して操作を進めない。

1. 利用可能なtool、app連携、terminalやbrowserの接続状態、対象windowやsessionの選択状態を確認し、参照できない理由を安全なread-only操作で調べる。
2. 一時的なtool失敗なら再試行し、利用中の生成AIツールが提供する標準的な再接続、再選択、権限確認の方法を特定して提示する。存在しないtool名や設定を推測で案内しない。
3. 回復に再起動、権限変更、install、設定変更などの副作用が伴う場合は、原因候補、影響、手順、期待結果を示してユーザーへ判断を求める。
4. 接続を回復できず、ユーザーから情報を受け取れば継続できる場合は、必要な出力または画面だけを具体的に依頼する。たとえば、直近のcommandと完全な出力、exit code、現在のURL、画面上のerror、再現操作を求める。
5. 貼り付けを依頼するときは、secretや個人情報を伏せるよう伝え、log全体ではなく診断に必要な範囲を指定する。
6. 必要な現在状態を取得できるまで、操作の成功、失敗原因、次に実行すべき変更を確定したものとして扱わない。

## 結果を引き渡す

次を簡潔に報告する。

- 観測した接続先と現在状態
- 会話から復元した目的と、実施した次の操作
- 完了条件を確認した観測点と検証結果
- 変更したファイル、実行したcommand、外部操作
- 残る不確実性、ユーザー判断、または貼り付けが必要な非機密情報
- コミットした場合はbranch、commit SHA、対象path

接続先を実際には観測できていない場合、その制約を明記する。推測した出力や未確認の結果を、観測済みの事実として報告しない。
