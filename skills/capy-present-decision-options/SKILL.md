# 判断すべき内容と選択肢を提示する

ユーザーにしか決められない論点を、作業を再開できる具体的な選択肢へ変換する。調査で解決できる事項や安全な実装判断を質問にせず、ユーザーの判断コストを必要最小限にする。

環境が構造化された選択・承認UIを提供している場合は、そのツールを使用してクリック可能な選択肢として提示する。テキストだけの選択肢は、適切なUIがない場合、自由記述が不可欠な場合、またはツールの制約で必要な選択肢を表現できない場合だけ使用する。UIを使う場合も、各選択肢の影響と推奨理由をツールの質問、ラベル、説明へ含める。

## 現在のコンテキストを把握する

1. ユーザーが達成したい結果、完了条件、明示された制約、すでに決まった事項、未完了の作業を整理する。
2. 利用可能なファイル、ログ、仕様、会話履歴、接続済みツールなど、現在のコンテキストから事実を確認する。容易に調査できる事実をユーザーへ質問しない。
3. 確認済みの事実、妥当な推定、未確認の仮定を区別する。推定や一般論をプロジェクト固有の事実として扱わない。
4. 判断を待たずに安全に進められる独立した作業があれば進める。必要な判断を理由に、無関係な作業まで停止しない。

## ユーザーが判断すべき論点だけを抽出する

次のいずれかに該当し、選択によって結果が実質的に変わる場合を判断事項とする。

- 目的、優先順位、期待する体験、許容可能な費用やリスクなど、ユーザーの価値判断が必要である。
- データ削除、公開、課金、送信、deploy、migration、履歴書き換えなど、不可逆または復旧コストの高い操作を伴う。
- credential、特権、外部システム、第三者への連絡など、エージェントの権限境界を越える。
- 複数の妥当な方針があり、互換性、保守性、納期、品質、費用などに意味のあるtradeoffがある。
- 不足情報を安全に推定すると、成果物や作業範囲がユーザーの意図から大きく外れる可能性がある。

次の事項は原則としてユーザー判断にしない。

- リポジトリの規則、既存contract、公式仕様、実行結果から一意に確認できる事実
- 依頼された範囲内の、可逆で局所的かつ通常の実装詳細
- 品質を下げずに採用できる標準的なdefault
- 作業を進めても後から低コストで変更でき、現時点の結果に重大な影響を与えない事項

判断事項が存在しない場合は、不要な選択肢を作らず、採用した妥当な前提を短く示して作業を続ける。

## 判断の順序と粒度を整える

1. 後続の選択肢を変える上流の判断を先にする。上流の回答が得られるまで意味を持たない質問はまだ提示しない。
2. 同じ決定で解消できる細かな質問を一つの論点へまとめる。一方の回答によって他方が自動的に決まる場合は別々に尋ねない。
3. 複数の独立した判断が同時に必要な場合は、作業を止めているものを優先し、通常は一度に三件以内に絞る。
4. 各論点について、なぜ今決める必要があるか、決定後に何が進むかを一文で説明できる状態にする。

## 選択肢を設計する

各判断には、実行可能で相互排他的な選択肢を通常二つから四つ提示する。

- 選択肢の名前を短くし、ユーザーが名前だけで回答できるようにする。
- 各選択肢に、実施内容、期待する結果、主な利点、欠点またはリスク、費用や所要時間などの重要な影響を記載する。
- 現在の目的と制約に基づいて一つを推奨し、推奨理由を具体的に説明する。
- 現状維持や延期が実行可能な方針である場合は、何が止まり、どのリスクが残るかを示した正式な選択肢として扱う。
- 実行不能、規則違反、または明らかに劣る案を、選択肢の数を増やすために含めない。
- 複数の案を自由に組み合わせるよう求めない。組み合わせが必要なら、意味のある組み合わせを独立した選択肢として定義する。
- 技術用語だけで差を表さず、ユーザーが観測する結果の違いに翻訳する。

推奨は中立を装わず、確認済みの要件を最もよく満たす案を選ぶ。ただし、根拠が不足して優劣を判断できない場合はその不足を明示し、最小限の追加確認または低コストの検証を先に提案する。

## 不確実性、不可逆性、権限境界を扱う

- 不明点が小さく、行動が可逆である場合は、明示した前提と安全なdefaultで進める。
- 不明点によって重大な損失、意図しない公開、互換性破壊、費用発生があり得る場合は、推測で進めず判断を求める。
- 追加調査によって選択肢を明確にできる場合は、まず安全なread-only調査を行う。ユーザーの価値判断を調査で代替しない。
- 不可逆な案には、対象、影響範囲、復旧可能性、backupやpreviewの有無、実行直前に再確認する事項を明記する。
- 権限や外部操作が必要な案には、誰が何を実行するか、必要な承認、credentialや秘密情報を共有せずに済む手順を明記する。
- 一時的な回避策やhackyな案は、長期的な保守性、security、data integrity、将来の移行コストを損なう可能性があれば推奨しない。妥当な恒久対応と並べ、例外的に選ぶ条件を示す。

## ユーザーへ提示する

必要な選択肢を表現できる構造化された選択UIを使用する。UIが利用できない場合、または選択肢数などのツール制約で表現できない場合は、最初に判断事項を一文の質問として示し、続けて選択肢を推奨順に提示する。各選択肢には少なくとも次を含める。

- 選択肢名。推奨案には明確に`推奨`と付ける。
- この案を選ぶと何を行い、何が得られるか。
- 重要なtradeoff、リスク、不可逆性、または必要な権限。

必要に応じて、その前に判断の背景として、確認済みの事実と未確認事項を短く示す。長い調査記録や思考過程を提示せず、選択に必要な根拠だけを残す。

最後に、回答方法を明示する。たとえば「Aで進めて」のように選択肢名だけで回答できる形にし、既定では自由記述の追加説明を必須にしない。推奨案をそのまま承認できる場合は、そのための短い回答も示す。

## 判断後に作業を再開する

1. 回答がどの選択肢を指すか確認し、選ばれた範囲を越えて解釈しない。
2. 判断内容、採用した前提、明示的に受け入れられたtradeoffを以後の作業条件として保持する。
3. 選択した案を実行する直前に前提や対象が変化していた場合は、古い承認を流用せず、変更点と影響を示して再確認する。
4. 判断によって可能になった作業を継続し、完了時に選択が結果へどう反映されたかを報告する。

ユーザーが選択していない案を暗黙に混ぜず、承認を将来の別操作やより広い権限への包括的な許可として扱わない。
