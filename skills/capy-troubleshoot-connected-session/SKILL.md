# 接続中のセッションをトラブルシュートする

現在接続しているターミナルとブラウザを一次情報として扱い、観測、仮説、再現、安全性の分類、修正、再確認を一つの診断ループとして進める。エラーを隠す回避策ではなく、保守可能な原因修正を優先する。

ユーザーに選択または承認を求める場合は、環境が提供する構造化された選択・承認UIを使用する。適切なUIがない場合だけ、テキストで選択肢や回答方法を提示する。

## 対象と権限を確定する

1. ユーザーの依頼、現在の作業ディレクトリ、接続中のターミナルやブラウザ、対象プロセス、期待する正常状態を確認する。対象が複数ある場合は、出力の時刻、URL、port、process、repository、branchを対応付ける。
2. リポジトリ内で作業する場合は、編集前に`AGENTS.md`、contribution guide、テスト手順、生成ファイル、コミットに関する指示を読む。worktree、現在のbranch、staged、unstaged、untrackedの状態を記録し、既存の変更をユーザーの作業として保全する。
3. このスキルを用いたトラブルシュートでは、workspace内でreview、revert、検証できる安全なコードやファイル修正と、その修正だけのコミットまでを依頼範囲に含める。ユーザーが診断のみ、read-only、またはコミット不要と指定した場合は、その境界を優先する。サービス再起動や外部システムへの書き込みは別途安全性を分類し、暗黙に許可されたとみなさない。
4. 正常状態が曖昧な場合は、既存のテスト、文書、設定、正常な隣接処理、ユーザーが示した期待値から判定基準を特定する。推測した基準は推測として明記する。

## 出力と証拠を観測する

1. 接続中のターミナルについて、現在のprompt、直近の完全なコマンド、終了code、標準出力と標準エラー、processが実行中か終了済みかを確認する。切れた末尾だけで判断せず、必要な範囲まで遡る。
2. 接続中のブラウザについて、表示中のURL、画面上のエラー、developer console、失敗したnetwork request、そのstatus、response、initiator、再現操作を確認する。可能なら画面の時刻とserver側logを対応付ける。
3. エラー文、stack trace、失敗したtest、request ID、timestamp、toolやruntimeのversion、直前の入力を記録する。診断に必要な最小限だけを扱い、log全体を無目的に複製しない。
4. token、cookie、password、authorization header、秘密鍵、個人情報、`.env`の値を表示、転載、コミットしない。必要なら値を伏せ、存在、形式、長さ、権限など秘密を露出しない属性だけを確認する。
5. 証拠が上書きされる可能性がある場合は、再起動、再実行、cache削除、生成物更新より先に必要な出力を保全する。ユーザーの既存logや成果物を編集しない。

確認済みの事実、そこから導いた仮説、まだ確認していない仮定を分けて整理する。典型的な文字列だけで原因を確定せず、最も説明力の高い仮説から検証する。

## 仮説を絞り最小再現を作る

1. 失敗箇所を、入力、アプリケーション、依存関係、runtime、OS、network、認証、権限、外部serviceの境界に分ける。
2. 各仮説について、現在の証拠、反証となる観測、次に行う最小のread-only確認を定める。安価で安全かつ識別力の高い確認を先に行う。
3. 元の入力、version、環境差を保ったまま、失敗を再現する最小のコマンドまたは操作を作る。再現のために本番データ、秘密情報、外部への副作用を必要とする場合は、fixture、dry-run、read-only endpointなどへ縮小する。
4. 再現しない場合は、最初の出力との差分、processの状態、時刻依存、cache、race、network、外部serviceを調べる。再現しなかったことを解消の証明にしない。
5. 複数の変更を同時に試さない。各確認または修正がどの仮説を支持・棄却したか追跡できる状態を保つ。

## 対応の安全性を分類する

対応候補を実行前に次のいずれかへ分類する。

### エージェントが実施できる安全な対応

ユーザーが修正を依頼しており、対象リポジトリまたは作業ファイルの範囲内で、容易にreview、revert、検証できる最小の変更を行う。たとえば、原因となるコード、テスト、repository内設定、文書、依存関係宣言の修正が該当する。

以下は安全な対応に含めない。

- `sudo`などの特権昇格、OSやhost全体の設定変更、権限や所有者の広範な変更
- databaseやuser dataの削除、migrationの強制適用、履歴書き換え、強制push、復元困難なcleanup
- firewall、認証、証明書、credential、production service、共有環境への変更
- 安全機構、validation、test、TLS、認証、権限制御を無効化して通す対応
- packageやtoolのglobal install、無制限なversion固定、原因不明のcache全削除

### ユーザーの実行または判断が必要な対応

特権、破壊的操作、共有環境、秘密情報、課金、production、物理device、広範なmachine設定に関わる場合は、自動実行しない。次を整理してユーザーへ引き渡す。

- 確認できた症状と原因、または原因候補
- なぜエージェントが実行しないか、影響範囲、失敗時のリスク
- backup、preview、dry-run、対象確認などの前提条件
- ユーザーがそのままコピーできる、対象を限定したコマンド
- placeholderがある場合の置換箇所と、実行前に確認すべき具体的な値
- 期待される出力、停止すべき出力、可能ならrollback手順

コマンドは一つずつ提示し、未解決のglob、曖昧なprocess名、広範な再帰対象を使わない。確認コマンドと変更コマンドを分け、秘密値をcommand historyへ残す形を避ける。ユーザーが実行したと報告するまで、成功したものとして先へ進めない。

### 判断を仰ぐ対応

短期的には動作しても、次のような長期的な不利益が見込まれる場合は適用せず、恒久対応、限定的な暫定対応、現状維持の選択肢を示して判断を仰ぐ。

- unsupported versionへの固定や不用意なdowngrade
- retry、timeout、resource上限を根拠なく増やして症状を隠す変更
- private API、monkey patch、手動生成物編集、再現不能なlocal-only workaround
- testの削除や緩和、errorの握り潰し、型やsecurity checkの無効化
- 将来のupgrade、運用、データ整合性、securityを悪化させるcompatibility hack

各選択肢について、解消可能性、変更範囲、保守負担、rollback、未解決リスクを比較し、推奨案とその根拠を明記する。

## 原因を修正する

1. 症状ではなく確認できた原因に対する最小の変更を行う。無関係なrefactor、format、dependency updateを混ぜない。
2. 変更前の再現手順を、可能な限り失敗するregression testへ落とし込む。外部環境依存で自動化できない場合は、手動確認手順と限界を記録する。
3. 修正後に対象test、関連する必須check、formatや静的解析を実行する。変更によって生成物が影響を受ける場合は、リポジトリの正規手順だけで更新する。
4. diffとstatusを確認し、秘密情報、debug出力、一時ファイル、無関係なユーザー変更が含まれていないことを確認する。
5. ユーザーがコミット不要またはread-onlyと指定しておらず、リポジトリの方針で許可され、修正と検証が完了した場合はコミットする。コミット前に対象pathとdiffを再確認し、今回の修正だけをpath単位でstageする。既存のstaged変更を巻き込まず、`git add .`や`git add -A`を使わない。原因と恒久的な意図を表すmessageにする。
6. protected branchまたはデフォルトブランチへ直接コミットしない。必要なbranch運用が不明な場合や、既存変更と安全に分離できない場合は、コミットせずユーザーに確認する。

## 解消を再確認する

修正方法にかかわらず、元の失敗を確認したのと同じ観測点で再確認する。

1. 最小再現を再実行し、終了code、期待出力、errorやwarningの消失を確認する。
2. 元のターミナル操作またはブラウザ操作を繰り返し、必要ならbrowser console、network request、server logの両側を確認する。
3. 周辺のregression testと必須checkを実行し、局所的にerror表示だけが消えた状態と区別する。
4. 再起動や再接続が必要なら、対象processと状態を特定し、安全に実行できる範囲か再分類する。無関係なserviceをまとめて再起動しない。
5. 解消しない場合は、新しい証拠を反映して仮説を更新し、観測からループを続ける。同じ操作を根拠なく繰り返さない。
6. ユーザー実行が必要な手順を提示した場合は、その後に貼り付けてもらう非機密の出力または再確認コマンドを明記する。実行結果を観測できるまで、解消済みと報告しない。

## 結果を引き渡す

次を簡潔に報告する。

- 観測した症状と、正常状態の判定基準
- 確認できた根本原因、棄却した主要仮説、残る不確実性
- 変更したファイルと挙動、またはユーザーに委ねた操作と理由
- 実行した再現・検証コマンド、その終了codeと結果
- コミットした場合はbranch、commit SHA、対象path
- ターミナルとブラウザのどの観測点で解消を確認したか
- 未解決なら、次に必要な非機密の証拠、判断事項、安全な選択肢

一時的に一度成功した、processを再起動した、error表示が消えたという事実だけで根本解決と報告しない。未確認の外部環境やユーザー操作を、完了したものとして扱わない。
